# 04 — воркспейсы (go.work)

**Workspaces** (Go 1.18, 2022) позволяют работать сразу с несколькими
локальными модулями как с единой сборкой — без `replace` и без публикации.

## Зачем

Раньше для одновременной разработки приложения и его библиотеки приходилось
прописывать `replace` в каждом `go.mod` (см. пример 03) и не забывать убрать
его перед коммитом. `go.work` решает это на уровне окружения разработчика.

## Структура примера

```
04_workspaces/
├── go.work            # use ./app  ./greeting
├── greeting/          # модуль-библиотека
│   ├── go.mod
│   └── greeting.go
└── app/               # приложение (require greeting, БЕЗ replace)
    ├── go.mod
    └── main.go
```

`go.work`:

```
go 1.21

use (
	./app
	./greeting
)
```

## Запуск

Из корня воркспейса (там, где `go.work`):

```sh
cd 28_modules/04_workspaces
go run ./app
```

Вывод:

```
Привет из воркспейса, мир!
```

## Команды

| Команда | Что делает |
|---|---|
| `go work init ./app ./greeting` | создать go.work и добавить модули |
| `go work use ./other` | добавить ещё модуль в воркспейс |
| `go work sync` | синхронизировать версии зависимостей между модулями |

## replace vs go.work

| | `replace` | `go.work` |
|---|---|---|
| Где живёт | в `go.mod` | отдельный `go.work` |
| Попадает в git | да (виден всем) | обычно нет (личное окружение) |
| Сколько модулей | подмена по одному | много модулей сразу |
| Назначение | форки, патчи версий | локальная мультимодульная разработка |

> `go.work` принято добавлять в `.gitignore`, чтобы он не навязывал ваши
> локальные пути остальной команде.
